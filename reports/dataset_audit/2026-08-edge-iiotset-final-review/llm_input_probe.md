# LLM 输入长度与序列化探针

## 实测样例

从 7 组真实 PCAP 重建会话，固定抽取 300 个会话并生成紧凑 JSON 风格 Evidence Card。当前环境没有 Qwen tokenizer，因此只报告字符数和 `chars/4`–`chars/3` 的近似 token 区间。

| 输入 | 字符中位数 | 字符 P95 | 近似 token 说明 |
|---|---:|---:|---|
| 前 8 包 + 会话摘要 | 490 | 534 | 多数低于约 180 tokens |
| 前 16 包 + 会话摘要 | 490 | 927 | 多数低于约 310 tokens；中位数相同源于大量短会话 |
| 前 32 包 + 会话摘要 | 490 | 1,705 | P95 约 426–568 tokens |
| 16 包 + 60 秒上下文摘要 | 686 | 1,123 | 中位约 172–229 tokens |
| 再加少量应用层证据 | 923 | 1,360 | 中位约 231–308 tokens |
| 再加约 1,800 字符 RAG | 2,732 | 3,169 | 中位约 683–911 tokens |

该结果只证明长度在 Qwen 常见上下文范围内，不代表信息质量已经验证。正式服务器环境应使用所选 Qwen tokenizer 重新计数。

## 初始建议（尚未冻结）

- 数据层保留最多前 16 包，模型输入采用可变长序列；短会话不补造包，显式 mask。
- 以“8 包 + 会话摘要”为低成本初始输入，16 包作为扩展/消融；32 包只在长会话或 Agent 请求时提供。
- 数值使用明确单位的整数或有限小数；方向使用 `C2S/S2C`，flags 使用稳定集合，不直接序列化浮点噪声。
- 基础白名单为方向、包长、IAT、协议/flags、持续时间、双向包/字节和缺失声明；端口与应用证据遵循 `raw_schema.md` 的条件白名单。
- 训练数据若选 100,000 张约 3 KB 的卡，未压缩 JSONL 约 300 MB；100 万张约 3 GB。正式规模应在去重、按类/活动采样后决定。
- 服务器通常只需上传冻结后的 session Parquet/JSONL、上下文索引、Schema 和 manifest，预计从数百 MB 到数 GiB，而不是上传 11.25 GB 解压原始数据。
